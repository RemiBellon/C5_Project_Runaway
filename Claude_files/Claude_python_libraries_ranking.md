# Ranking Your Python Libraries for a Runaway-Electron / Boris-Pusher Project

## TL;DR
- **Your single most important tool is not on your list: it is Numba (`@njit`).** For a tight, sequential Boris time-stepping loop on a laptop, Numba compiles a plain Python loop over particles to near-C speed while keeping float64 and full readability; NumPy-vectorized-over-particles with a Python time loop is the good-enough fallback, and JAX (`lax.scan` + `jit` + `jax_enable_x64`) is the power option once you want GPU ensembles. CuPy is a trap for a *conservation study on a laptop* because consumer GeForce GPUs run float64 at 1/32–1/64 of float32 (the RTX 4090 is exactly 1:64 — 1.29 TFLOPS FP64 vs 82.58 TFLOPS FP32).
- **Of your listed "Scientific Computation" tier, JAX and NumPy are Tier 0, Diffrax is Tier 1 (but only as an SDE engine for the collision operators and as a reference RK solver — NOT as a replacement for Boris), CuPy is Tier 2/3, and NumPyro/Py-PDE/CVXPY are Tier 3 (irrelevant).** The vast majority of your DataFrames/Web/AI/GUI lists are Tier 3 for this project.
- **The libraries you should install that you did NOT list are the real backbone: Numba, Matplotlib, SciPy, pytest, Hypothesis, h5py, xarray, PlasmaPy, Pint or astropy.units, SymPy, tqdm, and uv.** Add Polars/DuckDB only for the parameter-sweep results table (they are excellent there and wrong for raw trajectories, where HDF5/Zarr win).

## Key Findings

1. **The Boris loop is sequential in time but embarrassingly parallel over particles.** This dictates everything: you cannot parallelize the timestep axis, so per-step Python overhead is the enemy. The winning strategies are (a) compile the whole loop (Numba/JAX) or (b) vectorize across the particle axis so each Python step does one big array op. Both are legitimate; Numba is the least-effort high-performance answer on a CPU laptop.

2. **Boris is a *structure-preserving* integrator, not a generic ODE method.** Qin, Zhang, Xiao, Liu, Sun & Tang, "Why is Boris algorithm so good?" (Phys. Plasmas 20, 084503, 2013, doi:10.1063/1.4818428) state verbatim: *"We show that the Boris algorithm conserves phase space volume, even though it is not symplectic. The global bound on energy error typically associated with symplectic algorithms still holds for the Boris algorithm."* That bounded energy error is exactly why it survives 1e6–1e8 steps. Higuera & Cary (Phys. Plasmas 24, 052104, 2017, doi:10.1063/1.4979989) proved the relativistic Boris and Higuera–Cary schemes are volume-preserving while Vay (2008) is not — as Ripperda et al. (ApJS 235, 21, 2018) summarize: *"the Boris scheme and the Higuera–Cary scheme are volume preserving but the Vay scheme is not."* A generic adaptive RK (Dopri5/Tsit5) has *no* such property and will secularly drift in energy — so Diffrax's RK solvers are a validation reference, never a substitute for Boris.

3. **JAX defaults to float32, which is catastrophic for long-time conservation studies.** You must call `jax.config.update("jax_enable_x64", True)` at startup (or set `JAX_ENABLE_X64=True`). Consumer GPUs compound this: the RTX 4090 runs FP64 at 1/64 of FP32 (1.29 TFLOPS FP64 vs 82.58 TFLOPS FP32 per the Ada Lovelace specs), and the RTX 5090 keeps the same 64:1 gap (1.64 vs 104.8 TFLOPS). This means a laptop GPU is often *slower* than your CPU for a float64 conservation study, and only pays off for large float64-tolerant ensembles.

4. **A mature Python plasma ecosystem already exists and you should mine it for validation and physics helpers**, especially PlasmaPy (which ships `BorisIntegrator`, `RelativisticBorisIntegrator`, a `ParticleTracker`, and an NRL-formulary of plasma parameters), plus the JAX-fusion world (DESC, ESSOS, TORAX) and the runaway-electron-specific codes DREAM, KORC and SOFT.

5. **Radiation reaction breaks the volume-preserving structure of Boris**, so Stage 3 of your plan is a genuine research question, not a formality. The standard method (Tamburini et al., NJP 12, 123005, 2010) keeps the Boris push and adds the Landau–Lifshitz force as an operator-split sub-step; the RR force is dissipative and contracts phase-space volume (Lehmann & Spatschek, PRE 85, 056412, 2012; Hazeltine & Mahajan, PRE 70, 046407, 2004), so your conservation diagnostics must change accordingly.

## Detailed Tiered Ranking

### Tier 0 — Essential, build the project on these

**NumPy** — the substrate. Every state vector (position, momentum, 6-D phase space), every field evaluation, every diagnostic is a NumPy array. Even your JAX/Numba kernels consume and return NumPy. Non-negotiable. Use `float64` everywhere for the conservation work.

**Numba (`@njit`) — NOT on your list; this is the flagged critical omission.** For a laptop-only project whose core is a sequential stateful loop, Numba is the highest value-per-effort tool available. You write the Boris update as an explicit Python `for` loop over timesteps with an inner vectorizable operation over particles, decorate with `@njit(cache=True)`, and get compiled machine code at essentially C speed while staying in pure float64 Python. Numba's own docs report `parallel=True`/`prange` giving ~5× over NumPy for reduction-style loops; general third-party reports show 25–35× over pure Python for tight numerical loops. **Critical caveat: do NOT use `fastmath=True` in the pusher.** `fastmath` allows the compiler to reorder floating-point operations and use lower-accuracy (4-ULP) intrinsics, which breaks the exact cancellations that give Boris its bounded energy error; reserve `fastmath` (if ever) for non-conservation diagnostics. Use `cache=True` to avoid recompiling each run. Where in the code: the `push_boris`, `push_higuera_cary`, `push_vay` kernels, and the field-evaluation functions.

**Matplotlib — NOT on your list; second flagged critical omission.** AJP/EJP/Physics of Plasmas require publication-quality vector figures (PDF/EPS), controllable fonts, and full layout control. Matplotlib is the only tool here that produces submission-ready figures: energy-error-vs-time curves, μ and p_φ conservation plots, Poincaré maps, poloidal-plane orbit projections. Plotly (which you listed) is for *interactive* exploration, not for the final PDF. Install Matplotlib first; it is used in every stage.

**pytest + Hypothesis — NOT on your list; the robustness backbone you explicitly want.** pytest is the standard test runner. Hypothesis is property-based testing and it maps *perfectly* onto physics invariants: instead of testing one hand-picked case, you declare a property that must hold for randomized inputs and Hypothesis searches for counterexamples and shrinks them to a minimal failing case. The SciPy-proceedings paper "Falsify Your Software: validating scientific code with property-based testing" documents exactly this pattern (round-trip, metamorphic, and invariant properties) and is worth citing in your methods section. Concrete mappings for your project:
- *Invariant:* for uniform B and E=0, |v| and μ = mv⊥²/2B are conserved to tolerance for **any** randomized initial velocity/pitch → `@given` random v0, B.
- *Metamorphic:* rotating the field and initial condition by an arbitrary rotation must rotate the trajectory identically (isotropy).
- *Metamorphic:* halving dt must reduce the energy error consistent with the scheme's order (2nd order for Boris).
- *Invariant:* in axisymmetric tokamak geometry, canonical toroidal momentum p_φ is conserved for any starting point on a flux surface.
This is the single strongest robustness argument you can put in the paper.

**SciPy — NOT on your list.** You will need it constantly: `scipy.integrate` (RK45/DOP853/Radau as an independent reference integrator to benchmark Boris against), `scipy.interpolate` (spline interpolation of the analytic/tabulated flux function ψ and B-field, exactly as BEAMS3D and KORC do), `scipy.optimize` (finding the magnetic axis, root-finding for the Cerfon–Freidberg boundary coefficients), `scipy.fft`, and `scipy.constants` (exact e, m_e, c). Tier 0.

### Tier 1 — High value, adopt early

**JAX — Tier 1, becomes Tier 0 if you go the GPU/ensemble or autodiff route.** JAX is the right power-tool for the ensemble and Monte-Carlo stages. Key idioms:
- **Time loop:** implement the pusher inside `jax.lax.scan` (not a Python loop and not `fori_loop` — `scan` lowers to a single `WhileOp`, avoids unrolling huge XLA graphs, and is the recommended way to accumulate a trajectory). Carry the state `(x, p)` as the scan carry, emit diagnostics as the stacked `y` output. Keep the carry small.
- **Ensemble:** `jax.vmap` the single-particle pusher across your 1e3–1e5 particles — this is the embarrassingly-parallel axis.
- **float64:** you MUST set `jax.config.update("jax_enable_x64", True)` at import time or everything silently runs float32 and your energy conservation study is worthless. This is the "JAX default-float32 trap." Note `jax.random` also needs explicit float64 dtype even after enabling x64.
- **PRNG advantage:** JAX's explicit, splittable PRNG key system (`jax.random.split`) is a genuine *reproducibility advantage* for the stochastic collision operators — every random draw is a pure function of an explicit key, so your Monte-Carlo runs are bit-reproducible and trivially parallelizable across particles without correlated-stream worries. This is a real selling point for the paper's reproducibility section.
- **Autodiff:** if you pursue the guiding-center vs full-orbit validity angle, JAX gives you ∇B, curvature, and the field Jacobian by automatic differentiation of the analytic ψ — no hand-derived or finite-difference field gradients. This is how DESC/ESSOS/TORAX operate.

**Diffrax — Tier 1, but with a sharp boundary on WHERE.** Diffrax is a JAX-based ODE/SDE/CDE solver library by Patrick Kidger. Resolving your explicit question:
- **As a Boris replacement: NO.** Boris exploits the rotation+acceleration splitting of the Lorentz force; it is not a generic RK step. Diffrax *does* ship a `SemiImplicitEuler` symplectic solver for separable Hamiltonian systems, but it does not implement Boris/Higuera–Cary/Vay, and its adaptive RK solvers (Dopri5/Tsit5/Dopri8) are exactly the non-structure-preserving methods you are benchmarking *against*. Do not integrate the Lorentz force with a generic Diffrax solver and expect conservation.
- **As a reference/ground-truth solver: YES, excellent.** Use `Dopri8` or `Tsit5` with a tight `PIDController` tolerance as an independent high-order solution to benchmark your Boris trajectories against over moderate times. This is a clean, citable validation strategy.
- **For the collision operators (Stage 4): YES, this is its killer feature here.** Diffrax has real SDE solvers (`Euler`/Euler–Maruyama, `Heun`, Milstein-type, and specialized additive-noise solvers `SRA1`/`ShARK`, plus dedicated Underdamped Langevin solvers), explicit Itô-vs-Stratonovich handling, and Brownian-motion management. Your Boozer–Kuo–Petravic / Langevin pitch-angle scattering operator is exactly an SDE; Diffrax gives you tested, convergent SDE integration instead of a hand-rolled Euler–Maruyama.
- **Event handling: YES.** Diffrax's event system detects state crossings — useful for wall/loss detection and for triggering Poincaré section crossings.

**PlasmaPy — NOT on your list; Tier 1 and arguably should be higher.** This is the open-source Python plasma package and it is directly on-target. It provides `plasmapy.simulation.particle_integrators.BorisIntegrator` and `RelativisticBorisIntegrator` (with the exact `push(x, v, B, E, q, m, dt)` signature — e.g. `x_t1, v_t1 = BorisIntegrator.push(x=x_t0, v=v_t0, B=B, E=E, q=1.0, m=1.0, dt=0.01)` yields `x_t1 = [[0.04993754, -0.00249844, 0.]]`, `v_t1 = [[4.9937539, -0.24984385, 0.]]` for B=[0,0,5], v0=[5,0,0] — ready-made doctest cases you can assert against), a `ParticleTracker` with adaptive timestep and save/termination routines, and — most valuable — `plasmapy.formulary` (the NRL Plasma Formulary: gyrofrequency, gyroradius, ExB_drift, thermal speeds, collision frequencies). Use PlasmaPy as (a) an **independent implementation to cross-check your own Boris pusher** against on the drift test cases (their ExB and grad-B drift notebooks are ready-made verification cases), and (b) a source of correctly-implemented plasma-parameter formulas so you don't re-derive them with sign errors. Do not build *on top* of it as a dependency for your core loop (you want to own that code for the paper), but absolutely use it for validation. Note: plain `BorisIntegrator` is non-relativistic; use `RelativisticBorisIntegrator` for REs.

**Pint or astropy.units — NOT on your list; Tier 1 for correctness.** You emphasized careful normalization, and a units library is the standard way to catch unit/sign/scale errors before they silently corrupt a 1e8-step run. astropy.units integrates natively with PlasmaPy (eV↔K equivalencies, dimensionless-angle handling); Pint is the lighter standalone choice and integrates with xarray. **Decision rule:** use units at the *boundaries* (config parsing, setting up B0, R0, E∥, particle energy in MeV, converting to your normalized simulation units) — NOT inside the hot loop, where you strip to plain float64 in a documented normalized system (normalize time to gyro-period Ω⁻¹, B to B0, velocity to c, as is standard in PIC codes like Smilei). This gives you the safety of dimensional checking at setup without the per-step overhead.

**SymPy — NOT on your list; Tier 1 for this specific project.** This is genuinely valuable and under-appreciated. SymPy lets you (a) **derive and verify the Cerfon–Freidberg / Solov'ev analytic Grad–Shafranov ψ symbolically** — the 7 homogeneous polynomial basis functions ψ_i and the particular solution ψ_p = (P·R⁴/8 + (1−P)·(R²/2)·log R) are exactly the kind of closed-form expressions SymPy handles, and you can solve the 7×7 linear system for the c_i coefficients symbolically (Cerfon & Freidberg, "One size fits all analytic solutions to the Grad–Shafranov equation," Phys. Plasmas 17, 032502, 2010); (b) **compute B = ∇ψ×∇φ/R and its derivatives (∇B, curvature) analytically** and then `sympy.lambdify` them into fast NumPy/JAX functions — eliminating a whole class of hand-differentiation bugs in your grad-B and curvature drifts; (c) derive and check the guiding-center μ corrections symbolically. This directly serves robustness: the field and its gradients are provably consistent.

**h5py (HDF5) — NOT on your list; Tier 1 for trajectory data.** See the data-management analysis below. This is the correct format for large multi-dimensional trajectory arrays.

**tqdm — NOT on your list; Tier 1 quality-of-life.** Progress bars for the long single-particle integrations and ensemble sweeps. Trivial, but you'll want it for 1e8-step runs.

**uv — NOT on your list; Tier 1 for reproducibility.** uv (by Astral, Rust-based) is the modern package/environment manager. Its `uv.lock` cross-platform lockfile pins every transitive dependency exactly, which is precisely what a reproducible-computational-physics paper needs (reviewers/Zenodo archive can reproduce your exact environment). Replaces pip+virtualenv+pyenv+pip-tools with one fast tool. Decision rule: use uv over conda unless you need conda-only binary packages.

**Ruff — ON your list; Tier 1.** Ruff (also Astral) is an extremely fast linter+formatter. It is the right choice: near-instant, replaces flake8+isort+black, catches real bugs (unused variables, shadowing, undefined names) cheaply. Adopt from day one; it's part of the robust foundation. Pair with pre-commit.

**Pydantic + pydantic-settings — ON your list; Tier 1 for config validation.** This is a genuinely good fit. Your simulations have many parameters (B0, R0, a, elongation, triangularity, E∥, particle energy, pitch, dt, n_steps, RNG seed). Define a Pydantic model for the run configuration: it validates types, ranges (e.g. reject negative dt, pitch outside [−1,1], sub-Nyquist dt relative to the gyro-period), and gives you a single validated, serializable config object. `pydantic-settings` layers env vars / config files. This catches unit/sign/typo errors *before* a multi-hour run starts — direct robustness value. Where: the config-loading layer that feeds every simulation entry point.

## Critical Technical Investigations (resolved)

### (a) Numba vs JAX vs CuPy vs NumPy vs numexpr vs Cython for the Boris loop

**Decision: Start with Numba `@njit` on a particle-vectorized loop in float64. Move to JAX (`lax.scan`+`vmap`+`jit`, x64 enabled) when you want large ensembles or autodiff. Use plain NumPy-vectorized-over-particles as the readable reference implementation and for correctness cross-checks. Skip CuPy and numexpr for the core.**

Reasoning, per option:
- **(i) NumPy vectorized over particles, Python time loop:** Simplest and readable. Each timestep is a handful of big array ops over N particles, so Python overhead is amortized when N is large. Good enough for N≳1e4 and moderate step counts; it *is* your reference implementation. But for a single particle over 1e8 steps it is slow because Python-per-step overhead dominates.
- **(ii) Numba `@njit` over the whole loop:** Best CPU laptop answer. Compiles the entire time loop + particle loop to machine code; no per-step Python overhead; stays in float64 trivially. Reported speedups over pure Python are 1–2 orders of magnitude for tight loops; Numba's docs show `prange` parallel giving ~5× over NumPy. **Do not enable `fastmath`** in the pusher (breaks FP associativity/exact cancellation → corrupts the bounded-energy-error property). Use `@njit(cache=True)`; add `parallel=True`+`prange` only on the particle axis, never the time axis.
- **(iii) JAX `lax.scan`+`jit`:** The scalable/portable answer. `lax.scan` lowers the sequential loop to a single compiled `WhileOp` (avoids graph unrolling), `vmap` handles the particle axis, `jit` fuses it, and it runs on CPU or GPU unchanged. JAX docs and community benchmarks confirm `lax.scan` ≫ `fori_loop` > unrolled Python-for in compile+run efficiency. Must enable x64. Slight learning curve; the payoff is GPU portability + autodiff.
- **(iv) CuPy on a laptop GPU:** Only for large float64-tolerant ensembles; crippled by consumer-GPU FP64 (1/32–1/64; RTX 4090 = 1:64). Often slower than CPU for this study. Skip unless measured otherwise.
- **(v) numexpr:** Speeds single array expressions, not whole sequential loops; dominated by Numba/JAX. Skip for the core.
- **Cython (also not on your list):** A valid alternative to Numba — compiled, float64, fine-grained control — but higher friction (build step, type annotations, .pyx files) than Numba for identical performance in this use case. **Recommendation: prefer Numba over Cython** here; mention Cython in the paper as the "ahead-of-time compiled" alternative if a reviewer asks.

**GPU worth-it threshold:** roughly, GPU (JAX/CuPy) only pays off when you have ≳1e5 particles AND the per-step arithmetic is float32-tolerant OR you have a datacenter-class FP64 GPU (A100/H100). For float64 conservation work on a laptop, CPU+Numba wins. Also budget host↔device transfer: pulling diagnostics back every step destroys GPU speedup — accumulate diagnostics on-device inside `scan` and transfer once at the end.

### (b) float64 vs float32 and the JAX float32 trap

**Use float64 everywhere in the physics.** For 1e6–1e8-step conservation studies, float32 (≈7 decimal digits, ~1e-7 relative) accumulates round-off that swamps the discretization error you're trying to measure; you cannot distinguish scheme quality from float noise. float64 gives ~1e-15 relative.
- **JAX:** defaults to float32 to serve ML users; you MUST `jax.config.update("jax_enable_x64", True)` at startup (or `JAX_ENABLE_X64=True` env var). Per the JAX docs, *"by default jax_enable_x64 is set to False, and so jax.numpy array creation functions will default to returning 32-bit values."* `jax.random` needs explicit float64 dtype even then. This is the "sharp bit."
- **GPU FP64 penalty is real and severe on consumer cards:** the RTX 4090 runs FP64 at exactly 1/64 of FP32 (1.29 vs 82.58 TFLOPS); the RTX 5090 is the same 64:1 (1.64 vs 104.8 TFLOPS). As one analysis puts it, *"over 15 years… FP64 performance on consumer GPUs only increased 9.65× from 0.17 to 1.64 TFLOPS, while FP32 improved 77.63× from 1.35 to 104.8 TFLOP."* Datacenter A100/H100 have proper FP64 (A100 has dedicated FP64 cores + FP64 tensor cores at ~1:2). **Consequence:** a float64 conservation study on a laptop GeForce can be *slower* than the CPU. Apple Silicon/Metal has no mature float64 GPU path — CPU only there. **This is the single biggest practical trap in your GPU plan; document it in the paper.**

### (c) Diffrax — appropriate or trap?

Resolved above: **trap if used as a Boris substitute; high-value as (1) an SDE engine for the collision operators, (2) an independent high-order RK reference solver to benchmark Boris against, and (3) event handling for loss/Poincaré crossings.** Diffrax ships a `SemiImplicitEuler` symplectic solver (for separable Hamiltonians of the form dv/dt=f(t,w), dw/dt=g(t,v), including Hamiltonian systems) but no Boris/Higuera–Cary/Vay. Boris exploits Lorentz-force structure a generic solver cannot replicate, and Boris/HC are volume-preserving (Higuera & Cary 2017) whereas Dopri5/Tsit5 are not. For SDEs Diffrax offers Euler–Maruyama, Heun, additive-noise SRA1/ShARK, and Underdamped-Langevin-specific solvers with Itô/Stratonovich control — ideal for Boozer–Kuo–Petravic / Langevin pitch-angle scattering. **No public Boris-in-Diffrax implementation exists**; people do implement Boris directly in JAX (e.g. the PiC-Code-Jax repo has a JAX Boris pusher, and ESSOS traces particles in JAX), so your contribution of a clean structure-preserving JAX/Numba pusher + Diffrax SDE collisions is genuinely novel-ish and paper-worthy.

### (f) Data management — two different problems, two different answers

**Problem 1 — raw trajectories: "1e5 particles × N timesteps × 6 phase-space coords."** This is a large, dense, multi-dimensional numeric array. **Answer: HDF5 (h5py) or Zarr, NOT Parquet/Polars/DuckDB.** HDF5 is the computational-physics standard (BEAMS3D, KORC, DREAM all use it): chunked, compressed, supports unlimited/extendable time axis, rich attributes for metadata (units, config hash, seed), and partial reads. Zarr is the modern chunked alternative (better for cloud/parallel/larger-than-RAM + dask); it is the array analog of Parquet, optimized for n-dimensional arrays where Parquet's columnar/tabular model is a poor fit. For a laptop, **h5py is the pragmatic default**; add `xarray` on top for labeled access (dims: particle/time/coord). For quick scratch, `.npy/.npz` is fine but lacks metadata/chunking — don't use it for the archival dataset.

**Problem 2 — sweep results: "a table of 500 parameter-sweep runs with scalar summary diagnostics."** This is a *tabular* problem (rows = runs, columns = E∥, energy, pitch, seed, loss_fraction, final_energy, config_hash, ...). **Answer: Parquet + Polars or DuckDB.** This is exactly where Polars/DuckDB shine (4–10× faster than pandas, columnar, lazy/SQL, low memory). Write each run's summary row to `runs.parquet`; query/aggregate with Polars DataFrame API or DuckDB SQL. Keep a `config_hash` column linking each summary row back to its full HDF5 trajectory file — clean provenance.

**The sharp distinction:** raw trajectories → HDF5/Zarr (+xarray); sweep metadata/results → Parquet + Polars/DuckDB. Do not mix them up. DuckDB/Polars on raw 6-D trajectories is the wrong tool; HDF5 for a flat results table is clumsy.

**Minimal robust foundation to install on day one (all stages benefit):** NumPy, SciPy, Numba, Matplotlib, pytest, Hypothesis, Ruff, Pydantic, uv (env), tqdm, h5py, Git. This *is* "robust from the beginning" without over-engineering — it's ~12 well-chosen packages, all lightweight.

- **Stage 1 (drifts, μ):** add SymPy to derive ∇B/curvature analytically and `lambdify` them; cross-check drifts against PlasmaPy's `formulary` (ExB_drift, grad-B) and its drift notebooks. Still CPU/Numba.
- **Stage 2 (toroidal orbits, Solov'ev/Cerfon–Freidberg, passing/banana, p_φ):** SymPy to derive the analytic ψ and solve the 7-coefficient system; SciPy for magnetic-axis root-finding and spline interpolation if needed; Matplotlib for poloidal projections and the first Poincaré maps; add p_φ conservation as a Hypothesis property. Introduce **xarray** here if datasets get multi-dimensional.
- **Stage 3 (E∥ acceleration + synchrotron radiation reaction):** add the Landau–Lifshitz RR force as an operator-split sub-step after the Boris push (Tamburini et al., NJP 12, 123005, 2010 — keep the Boris pusher unchanged for the Lorentz force, add RR as a smaller sub-step). This is where you switch to strictly float64 and where the conservation diagnostics change (phase-space volume now contracts — Lehmann & Spatschek 2012; Hazeltine & Mahajan 2004 — so track it rather than expecting exact volume preservation). Consider the relativistic volume-preserving algorithm (Liu/Qin et al., Phys. Plasmas 23, 102502, 2016) as an alternative to plain Boris+RR for very-long-time (~1 s) runs where "global coherent accumulation of numerical errors" matters. Reference KORC/SOFT.
- **Stage 4 (relativistic Monte-Carlo collisions, Langevin SDE):** introduce **JAX** (x64!) + **Diffrax** SDE solvers (Euler–Maruyama/Milstein/SRA1) for the Boozer–Kuo–Petravic pitch-angle-scattering operator; use JAX's PRNG-key system for reproducible stochastic ensembles; `vmap` the ensemble. This is where GPU *might* help — but re-check the float64 penalty first.
- **Stage 5 (perturbed/stochastic fields, Poincaré, loss stats, ripple):** scale up ensembles (JAX `vmap`/`scan` or Numba `prange`); write results to `runs.parquet`; query with **Polars or DuckDB**; use **xarray** for the multi-dimensional loss datasets; optionally scikit-learn to classify orbit types; optionally Snakemake to orchestrate the sweep; optionally a Streamlit explorer. Archive to Zenodo for the paper.

## Caveats
- **Benchmark numbers are order-of-magnitude, not machine-specific.** Numba/JAX/Polars speedups (1–2 orders over pure Python; 4–10× Polars-over-pandas; ~5× Numba `prange`-over-NumPy) come from vendor docs and third-party benchmarks on other workloads; you must benchmark your own pusher on your own laptop. Treat all cited ratios as guidance. The FP64 ratios (RTX 4090 = 1:64) are exact hardware specs and reliable.
- **The claim "radiation reaction destroys Boris's volume preservation" is an inference** combining Qin et al. 2013 (Boris preserves volume) with Tamburini 2011 / Hazeltine–Mahajan 2004 / Lehmann–Spatschek 2012 (RR physically contracts phase-space volume). It is standard and robust but not stated as a single verbatim theorem; present it as reasoned, not quoted. KORC's exact pusher scheme name for the RR sub-step should be confirmed directly in its Fortran source (`korc_ppusher.f90`) if you need to cite it precisely.
- **Several list entries were mis-transcribed or unidentifiable:** "Turnover" (likely a vector-search DB — irrelevant), "Numpypro" (=NumPyro), "Niquest" (=Niquests), "Dspydantic" (=DSPy/instructor), "Monty", "Congee" (=Cognee), "TabFM" (=TabPFN), "Data-profiling" (=ydata-profiling), "Datarep", and "xy" (ambiguous plotting lib). None of the identified ones change the conclusions — they are all Tier 3 for this project.
- **PlasmaPy's plain `BorisIntegrator` is explicitly non-relativistic**; use `RelativisticBorisIntegrator` for REs, and note its relativistic corrections affect the leapfrog half-step. Cross-check accordingly.
- **This ranking is strictly for the runaway-electron/Boris-pusher project.** Many Tier 3 libraries (pandas, PyTorch, FastAPI, Streamlit) are excellent in general — they are simply off-target here.
